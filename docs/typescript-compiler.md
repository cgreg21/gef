# TypeScript compiler

GEF exposes a TypeScript project compilation API through `gnome-extension-framework/compiler` and the `gef compile-ts` CLI command.

```ts
import { compileTypeScriptProject } from 'gnome-extension-framework/compiler';

const result = compileTypeScriptProject({
  configFilePath: 'tsconfig.json',
  outDir: 'dist',
});

if (!result.success) {
  for (const diagnostic of result.diagnostics) {
    console.error(diagnostic);
  }
}
```

The compiler reads the project's `tsconfig.json`, performs TypeScript semantic checking, and emits JavaScript plus source maps. An optional `outDir` overrides the configured output directory. Type errors prevent output emission.

## Native compilation status

This is the TypeScript frontend milestone, not yet machine-code generation. GEF applications use different platform runtimes: GJS for GNOME Shell and Node-GTK for desktop GTK. The next stages are a shared typed intermediate representation, a GTK desktop executable backend, and platform-specific packaging. GNOME Shell extensions must continue to emit JavaScript compatible with GJS; they cannot be replaced by standalone ELF binaries inside the shell process.

## CLI

```sh
gef compile-ts
gef compile-ts tsconfig.json
gef compile-ts --project tsconfig.app.json
gef compile-ts --project tsconfig.json --out-dir dist
```

The command defaults to `tsconfig.json`, accepts `--project` / `-p` and an optional `--out-dir`, prints TypeScript diagnostics, and exits non-zero when the project cannot be compiled. Both project templates generated by `gef new` call `gef compile-ts` after compiling their GTPL template, so the generated application and GNOME Shell extension share the same TypeScript frontend. Existing `gef compile` remains dedicated to GTPL templates.


## Renderer-neutral UI IR

The compiler exports `compileGtplToUiIr(source)` from the package root. It validates and lowers a GTPL view into a renderer-neutral UI tree containing elements, properties, events, references, text, local declarations and control-flow nodes. Binding and control-flow expressions remain expression ASTs; the IR does not import GTK, GJS or Node-GTK and does not execute application code. A backend can consume this shape without depending on the GTPL parser's source-node representation.

Invalid templates return diagnostics and an empty IR. Structural directives and two-way bindings are lowered before the IR is created.

## TypeScript components and UI IR

`compileGtplComponentToUiIr(ComponentType, options)` connects a decorated TypeScript component to the renderer-neutral UI IR. It reads the root component's `@Component` template and accepts child component classes through `componentTypes`. Their selectors, `@Input` names and `@Output` names come directly from decorator metadata. Unknown selectors and invalid bindings produce GTPL diagnostics and an empty IR. Strict validation accepts native elements only when their names are listed in `nativeElements`; pass the target renderer's supported element names explicitly rather than relying on naming conventions.

`nativeElements` can be supplied for GTK or GNOME Shell actor names; project compilation shares this list across all templates. The compiler does not embed a platform-specific native registry. The root template's TypeScript members are supplied through `componentMembers` (and can be checked against `contextType`). The compiler does not instantiate application classes to discover instance fields. A native backend can consume the returned metadata and UI nodes without depending on GTK or GJS.

```ts
import { compileGtplComponentToUiIr } from 'gnome-extension-framework/compiler';

const result = compileGtplComponentToUiIr(EditorComponent, {
  componentMembers: ['title', 'save'],
  componentTypes: [SaveButtonComponent],
});
```


### Compiling a component set

For a project containing several decorated components, use `compileGtplComponentsToUiIr({ components })`. Register the component classes once; every template is then checked against the same selector, input and output contracts. Per-component `componentMembers`, `contextType` and external `templateSource` are supplied on each entry. The result preserves one `ComponentUiIrResult` per component, so diagnostics in one template do not discard valid IR from other templates.

```ts
const discovered = discoverTypeScriptComponents({ configFilePath: 'tsconfig.json' });\n// The descriptors are static source metadata; they are not instantiated classes.\n\nconst project = compileGtplComponentsToUiIr({
  components: [
    { type: EditorComponent, componentMembers: ['title', 'save'] },
    { type: SaveButtonComponent, componentMembers: ['label'] },
  ],
});

if (!project.success) {
  for (const component of project.components) {
    for (const diagnostic of component.diagnostics) {
      console.error(component.metadata.selector, diagnostic);
    }
  }
}
```

The registry is explicit and deterministic: duplicate selectors and classes without `@Component` metadata are rejected. The compiler still does not instantiate application classes. `discoverTypeScriptComponents({ configFilePath })` scans the source files selected by `tsconfig.json` and returns static descriptors for `@Component` classes, including selector, inline/external template, `@Input`, `@Output` and public instance member names. Discovery reads the TypeScript AST only and never imports application modules. Decorator options must be static object literals with string-literal values; dynamic expressions are reported as diagnostics rather than evaluated.


### Compiling discovered TypeScript components

Use `compileTypeScriptComponentsToUiIr({ configFilePath })` to connect static component discovery directly to the shared UI IR compiler. It discovers all `@Component` classes selected by `tsconfig.json`, builds one selector/input/output registry, and compiles every template without importing application modules.

Native element names remain target-specific and must be passed with `nativeElements`. External templates declared with `templateUrl` are read as UTF-8 files relative to the declaring TypeScript file. For virtual filesystems or tests, `templateSources` can override file contents by absolute resolved path. Missing files fail with a component-specific error. TypeScript discovery diagnostics are returned in `discoveryDiagnostics`; GTPL diagnostics remain attached to each component.

```ts
import { compileTypeScriptComponentsToUiIr } from 'gnome-extension-framework/compiler';

const project = compileTypeScriptComponentsToUiIr({
  configFilePath: 'tsconfig.json',
  nativeElements: ['StLabel', 'StButton'],
});
```


## GTK4 native C backend (experimental)

The compiler exports `emitGtkC(nodes)` from the package root. The backend supports static `GtkBox` and `GtkGrid` containers with `GtkLabel`, `GtkButton`, `GtkEntry` and `GtkCheckButton` children. Grid children accept `row` and `column` (defaulting to row 0 and their child index), plus positive `rowSpan` and `columnSpan` (default 1). For `GtkButton` click events, pass `callbacks` to `emitGtkC` or `compileGtkNative`: it maps a zero-argument GTPL handler such as `this.save()` to a C symbol. The callback implementation must be supplied in `nativeSources` and must use the GTK signal signature `void callback(GtkButton *button, gpointer user_data)`. GEF emits the declaration and `g_signal_connect`; it does not translate TypeScript method bodies into C. Unsupported event shapes are rejected. It emits a GTK4 C application using `GtkApplication`; compile the generated source with a C compiler and GTK4 flags from `pkg-config --cflags --libs gtk4`.

Bindings, events, references, control-flow nodes, unsupported properties and unsupported widgets are rejected with diagnostics. A failed result has an empty source string: unsupported IR is never silently omitted. This is a first static-code-generation milestone, not yet a complete TypeScript-to-native compiler or a CLI command.


## GTK4 native compilation API

`emitGtkC(nodes)` emits a static GTK4 C application for `GtkBox`, `GtkGrid`, `GtkLabel`, `GtkButton`, `GtkEntry` and `GtkCheckButton`. The asynchronous `compileGtkNative(nodes, { outputFile })` API compiles that source into a native executable using `pkg-config --cflags --libs gtk4` and a C compiler (default: `cc`). The compiler and pkg-config executable can be overridden with `compiler` and `pkgConfig`.

The build host must have GTK4 development files, `pkg-config` and a C compiler installed. Commands are invoked without a shell. Temporary C source is removed after compilation; the resulting executable is written to the requested output path. Unsupported widgets, bindings, events, references and control-flow nodes fail with diagnostics rather than being silently omitted. This backend currently targets GTK4/Linux; it is not yet a general TypeScript-to-native compiler.


## Native GTK4 CLI

On a Linux build host with GTK4 development files, `pkg-config` and a C compiler installed, compile a static GTK template directly to an executable:

```sh
gef compile-native src/app.gtpl dist/my-app
```

The output argument is optional; when omitted, the executable is written beside the template using its filename without the `.gtpl` suffix. The CLI accepts the native `GtkBox`, `GtkLabel`, `GtkButton`, `GtkEntry` and `GtkCheckButton` elements. Bindings, events, references, control-flow blocks and unsupported properties are rejected with source diagnostics. Repeat `--native-source file.c` to link callback implementations and `--callback method=symbol` to map a zero-argument GTPL handler to its C function (for example, `gef compile-native app.gtpl app --native-source src/callbacks.c --callback save=gef_on_save`). Callback method names must be unique and C symbols valid. This command compiles a static GTPL view; it does not yet compile decorated TypeScript components or their application logic. GNOME Shell extensions continue to use the separate GJS/JavaScript build.


### GTK native literal bindings

The GTK4 C backend accepts property bindings whose GTPL expression is a single non-null literal (string, number or boolean). These values are emitted as compile-time constants. Identifiers, member access, calls, operators, null and other runtime expressions remain unsupported and produce diagnostics; they are never silently replaced with defaults.
