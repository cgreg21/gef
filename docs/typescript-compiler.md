# TypeScript compiler

GEF exposes a TypeScript project compilation API through `gnome-extension-framework/compiler` and the `gef compile-ts` CLI command.

```ts
import { compileTypeScriptProject } from 'gnome-extension-framework/compiler';

const result = compileTypeScriptProject({
  configFilePath: 'tsconfig.json',
  outDir: 'dist',
});

if (!result.success) {
  for (const diagnostic of result.diagnostics) {
    console.error(diagnostic);
  }
}
```

The compiler reads the project's `tsconfig.json`, performs TypeScript semantic checking, and emits JavaScript plus source maps. An optional `outDir` overrides the configured output directory. Type errors prevent output emission.

## Native compilation status

This is the TypeScript frontend milestone, not yet machine-code generation. GEF applications use different platform runtimes: GJS for GNOME Shell and Node-GTK for desktop GTK. The next stages are a shared typed intermediate representation, a GTK desktop executable backend, and platform-specific packaging. GNOME Shell extensions must continue to emit JavaScript compatible with GJS; they cannot be replaced by standalone ELF binaries inside the shell process.

## CLI

```sh
gef compile-ts
gef compile-ts tsconfig.json
gef compile-ts --project tsconfig.app.json
gef compile-ts --project tsconfig.json --out-dir dist
```

The command defaults to `tsconfig.json`, accepts `--project` / `-p` and an optional `--out-dir`, prints TypeScript diagnostics, and exits non-zero when the project cannot be compiled. Both project templates generated by `gef new` call `gef compile-ts` after compiling their GTPL template, so the generated application and GNOME Shell extension share the same TypeScript frontend. Existing `gef compile` remains dedicated to GTPL templates.


## Renderer-neutral UI IR

The compiler exports `compileGtplToUiIr(source)` from the package root. It validates and lowers a GTPL view into a renderer-neutral UI tree containing elements, properties, events, references, text, local declarations and control-flow nodes. Binding and control-flow expressions remain expression ASTs; the IR does not import GTK, GJS or Node-GTK and does not execute application code. A backend can consume this shape without depending on the GTPL parser's source-node representation.

Invalid templates return diagnostics and an empty IR. Structural directives and two-way bindings are lowered before the IR is created.

## TypeScript components and UI IR

`compileGtplComponentToUiIr(ComponentType, options)` connects a decorated TypeScript component to the renderer-neutral UI IR. It reads the root component's `@Component` template and accepts child component classes through `componentTypes`. Their selectors, `@Input` names and `@Output` names come directly from decorator metadata. Unknown selectors and invalid bindings produce GTPL diagnostics and an empty IR.

The root template's TypeScript members are supplied through `componentMembers` (and can be checked against `contextType`). The compiler does not instantiate application classes to discover instance fields. A native backend can consume the returned metadata and UI nodes without depending on GTK or GJS.

```ts
import { compileGtplComponentToUiIr } from 'gnome-extension-framework/compiler';

const result = compileGtplComponentToUiIr(EditorComponent, {
  componentMembers: ['title', 'save'],
  componentTypes: [SaveButtonComponent],
});
```
